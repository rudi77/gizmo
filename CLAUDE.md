# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project at a glance

Gizmo is a small simulated quadruped (4 legs × 2 joints + 2 arms + head pan = 11 joints) running in **Gazebo Harmonic** with **ROS 2 Jazzy** on **Ubuntu 24.04 / WSL2**. The repo is a colcon workspace with three packages under `src/`:

- `gizmo_description` — URDF/xacro, ros2_control hookup, controller YAML.
- `gizmo_bringup` — launch file plus four Python nodes: `gizmo_gait_node`, `gizmo_face_node`, `gizmo_stt_node`, `gizmo_tts_node`.
- `gizmo_brain` — `gizmo_brain_node`, the LLM action router that maps `/gizmo/user_text` to movement/face/say topics (Iteration 5).

`build/`, `install/`, `log/` are generated by colcon and gitignored. `gizmo_description.txt` and `docs/PRD.md` / `docs/ROADMAP.md` capture intent (the latter two are written in German); the roadmap is the source of truth for iteration scope and done-criteria.

## Build & run

Every shell needs ROS sourced first. Build from the repo root, not from `src/`:

```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install        # rebuild after editing CMakeLists/package.xml; symlink-install lets you edit launch/scripts without rebuilding
source install/setup.bash              # re-source after each colcon build
ros2 launch gizmo_bringup gizmo_sim.launch.py
```

To rebuild a single package: `colcon build --symlink-install --packages-select gizmo_bringup`.

There is **no test suite, no linter, no CI**. "Done" for an iteration means the sim launches cleanly and the action is visibly correct in Gazebo (see `docs/ROADMAP.md` done-criteria).

## Driving the robot

The launch file brings up Gazebo, spawns Gizmo, starts `joint_state_broadcaster` + `gizmo_joint_trajectory_controller`, and runs `gizmo_face_node`, the long-running `gizmo_gait_node` in `action:=listen` (router) mode, `gizmo_brain_node`, plus the speech loop (`gizmo_stt_node` in `engine:=dummy` mode by default and `gizmo_tts_node` in `engine:=espeak`). To exercise behaviours, either talk to the brain on `/gizmo/user_text`, drive a layer directly via its topic, or run a one-shot `gizmo_gait_node` from a second shell:

```bash
# Talk to the brain (German or English; rule-based default backend).
ros2 topic pub --once /gizmo/user_text std_msgs/String "data: 'lauf nach vorne'"
ros2 topic pub --once /gizmo/user_text std_msgs/String "data: 'freu dich'"

# Bypass the brain and poke the routers directly.
ros2 topic pub --once /gizmo/movement std_msgs/String "data: 'crawl_forward'"
ros2 topic pub --once /gizmo/face std_msgs/String "data: 'happy'"

# One-shot gait test driver (own process, separate from the launch's
# router instance) — still works for tuning trajectories.
ros2 run gizmo_bringup gizmo_gait_node --ros-args -p action:=stand_pose
ros2 run gizmo_bringup gizmo_gait_node --ros-args -p action:=wave            # alias for wave_right
ros2 run gizmo_bringup gizmo_gait_node --ros-args -p action:=wave_left
ros2 run gizmo_bringup gizmo_gait_node --ros-args -p action:=arms_up
ros2 run gizmo_bringup gizmo_gait_node --ros-args -p action:=crawl_forward
# Combine: arms wave while crawling
ros2 run gizmo_bringup gizmo_gait_node --ros-args \
    -p action:=crawl_forward -p crawl_arm_action:=wave_right
# Face expressions: neutral | happy | sad | surprised | angry
# Status checks
ros2 control list_controllers
ros2 topic info /clock

# Speech loop (Iteration 6).
# TTS is wired up by default — anything published to /gizmo/say is spoken
# via espeak-ng (auto-falls back to log-only if the binary is missing).
ros2 topic pub --once /gizmo/say std_msgs/String "data: 'hallo, ich bin gizmo'"
# STT runs in dummy mode in the launch (no mic in the default sandbox);
# switch to a real microphone in a second shell:
ros2 run gizmo_bringup gizmo_stt_node --ros-args -p engine:=mic -p language:=de-DE
```

Crawl gait, wave timing, and arm-pose timing are exposed as ROS parameters on `gizmo_gait_node` (`crawl_frequency`, `crawl_step_length`, `crawl_swing_height`, `crawl_duty_factor`, `crawl_duration`, `arm_wave_cycles`, etc.) — tune from the CLI rather than editing source.

## Architecture you need to know before editing

### One controller, 11 joints, one trajectory topic

`gizmo_joint_trajectory_controller` (a `joint_trajectory_controller/JointTrajectoryController`) owns **all 11 joints** in a fixed order — see `JOINT_ORDER` in `src/gizmo_bringup/scripts/gizmo_gait_node.py:46`. Anything publishing trajectories must use that exact ordering. Adding a new joint means: add it to the URDF (`gizmo.urdf.xacro`), add a `<xacro:position_joint>` entry inside `<ros2_control>`, list it under `joints:` in `gizmo_controllers.yaml`, and append it to `JOINT_ORDER`. Forgetting any one of these will silently break gait/pose code.

The stand pose is symmetric (hips=0, knees=−0.6 rad). Spawn z in the launch file (`0.17 m`) was picked so feet just touch the ground at this pose — if you change leg geometry in `leg_macro.xacro`, recompute and update the spawn z.

### Face pipeline (ROS ↔ Gazebo)

`gizmo_face_node` subscribes to `/gizmo/face` (`std_msgs/String`) and publishes `/gizmo/face_color` (`std_msgs/ColorRGBA`). The launch file bridges `/gizmo/face_color` to `gz.msgs.Color` via `ros_gz_bridge`, and a `gz-sim-material-color-system` plugin attached to `display_link` in the URDF retints the visual. Add a new expression by extending the `EXPRESSIONS` dict in `gizmo_face_node.py` — that's the single source of truth, intentionally shared with the future Brain layer.

### Brain / action router (Iteration 5)

`gizmo_brain_node` subscribes to `/gizmo/user_text` (`std_msgs/String`) and emits one of three follow-up topics: `/gizmo/movement`, `/gizmo/face`, `/gizmo/say` (all `std_msgs/String`). The internal action JSON schema is documented in `docs/PRD.md` §4.4 and the allowed vocabularies live as `KNOWN_MOVEMENTS` / `KNOWN_EXPRESSIONS` tuples in `src/gizmo_brain/scripts/gizmo_brain_node.py` — keep them in sync with `JOINT_ORDER`-aware actions in the gait node and `EXPRESSIONS` in the face node. Backend is selected via the `backend` ROS parameter (`rule_based` | `openai` | `anthropic`); the cloud paths are stubs that fall back to the rule matcher unless the matching `*_API_KEY` env var is set, so the launch stays offline by default.

The gait node has a dual personality: with `action:=<name>` it fires once and then stays alive, and it always subscribes to `/gizmo/movement` so the brain can drive new actions later. The launch file spawns it with `action:=listen` to suppress the one-shot kick-off — that instance is the project's *movement router*. Adding a new movement means extending `_run_action` (and `KNOWN_MOVEMENTS` in the brain) so all three layers know about the same name.

### Speech loop (Iteration 6)

`gizmo_stt_node` and `gizmo_tts_node` close the voice loop without expanding the topic graph: STT publishes recognised text on `/gizmo/user_text` (the same topic the brain already consumes), and TTS subscribes to `/gizmo/say` (the same topic the brain already produces). Both are intentionally schema-free `std_msgs/String` so the layers stay swappable. Engines are pluggable via the `engine` parameter and **always degrade gracefully**: STT falls back to `dummy` (idle, log only) when `speech_recognition` or PortAudio is missing; TTS falls back to `dummy` when `espeak-ng`/`espeak` isn't on PATH. The launch ships STT in `dummy` so a sandbox without a mic still launches green; switch to `engine:=mic` in a second shell for live capture. The brain itself stays untouched — it already emitted `/gizmo/say` for the rule-based `sag …` / `say …` prefixes.

### Layering intent (Sim-First)

The architecture in `docs/PRD.md` is: `mic → stt → brain (LLM) → {movement, face, tts}`. Lower layers (movement / face / tts) **must not know about the brain**. The hardware port is meant to be a swap of the `ros2_control` hardware component only — keep topics and joint names stable when iterating. This is why the gait node speaks JointTrajectory and the face node speaks `std_msgs/String`: both interfaces survive the move from sim to real hardware.

### Launch-file traps already worked around

These are baked into `src/gizmo_bringup/launch/gizmo_sim.launch.py` and `src/gizmo_description/urdf/gizmo.urdf.xacro` — preserve them when refactoring:

- **Controllers YAML path**: modern Gazebo does **not** expand `$(find pkg)` inside `<plugin>/<parameters>`. The launch file resolves the YAML to an absolute path and passes it into xacro as `controllers_yaml:=...`; the URDF reads it via `<xacro:arg name="controllers_yaml">` and emits an absolute path into `<parameters>`.
- **`robot_description` typing**: the xacro `Command` substitution is wrapped in `ParameterValue(..., value_type=str)`. Without this, `robot_state_publisher` tries to YAML-parse the URDF and fails with "Unable to parse the value of parameter robot_description as yaml".
- **`/clock` bridge is mandatory**: controllers run with `use_sim_time=true`. Without the `parameter_bridge` for `/clock@rosgraph_msgs/msg/Clock[gz.msgs.Clock`, controller_manager service callbacks stall and spawners time out.
- **Spawner timing uses `TimerAction`, not `OnProcessExit`**: chaining off `ros_gz_sim create` exiting is racy because `create` exits before controller_manager advertises its services. Current values: spawn at 4 s, JSB at 8 s, JTC at 12 s, gait_router at 14 s, brain at 15 s, all with `--controller-manager-timeout 60`. If you add controllers, slot them after JTC with a similar margin; layer-router nodes go after the gait router. The Iteration-6 STT/TTS nodes don't talk to controllers at all and start immediately with the rest of the launch.

## Conventions

- **CMakeLists install whitelist**: `gizmo_description/CMakeLists.txt` installs `urdf meshes config launch`; `meshes/` and `launch/` exist but are still empty (reserved for later iterations). If you add resources, put them in those directories rather than inventing new ones.
- **Adding a new Python node** in `gizmo_bringup`: drop it under `scripts/`, add an `install(PROGRAMS … RENAME …)` block to `CMakeLists.txt` (note the rename strips the `.py`), and add the relevant `<exec_depend>` to `package.xml`.
- **Iteration workflow**: each iteration in `docs/ROADMAP.md` corresponds to a feature branch and a PR. Don't merge before the documented done-criteria pass in sim. New features layer onto the existing topology — they don't replace the movement/face/brain/speech split.
- **Shell scripts** (`scripts/01_install_gazebo_ros2_wsl2.sh`, `02_test_gazebo.sh`) use `set -eo pipefail` (no `-u`) on purpose: ROS setup scripts reference unbound vars and trip `nounset`.

## Environment notes (WSL2)

The install script and smoke test under `scripts/` target Ubuntu 24.04 (noble) on WSL2/WSLg. If `gz sim` can't find a display, run `wsl --update && wsl --shutdown` from elevated PowerShell, then verify `$DISPLAY` and `$WAYLAND_DISPLAY` are set in a fresh shell.
